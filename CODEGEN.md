# CODEGEN.md — Luandro Native Runtime Platform
# Code Generation Strategy
# Phase 0.7 — Code Generation & Automation Strategy
#
# The generator is the single source responsible for producing repetitive code.
# API Specifications (ASL) are the single source of truth.
# Generated code MUST NEVER be edited manually.

---

## 1. Core Principle

```
ASL Specification (.yaml)
         │
         ▼
   Binding Generator
         │
    ┌────┴────────────────┐
    │                     │
    ▼                     ▼
Generated Kotlin     Generated C++/JNI
(generated/kotlin/)  (generated/jni/, generated/native/)
         │
         ▼
Generated Luau Binding
(generated/luau/)
         │
         ▼
Generated Docs + Test Skeletons
(generated/docs/)
```

> **Rule**: `generated/` directory is NEVER committed to git and is ALWAYS reproducible.

---

## 2. Generator Responsibilities

The Binding Generator produces:

| Output | Location | Description |
|--------|----------|-------------|
| Kotlin wrapper classes | `generated/kotlin/` | Public API classes |
| Kotlin native declarations | `generated/kotlin/` | `external fun` declarations |
| JNI registration | `generated/jni/` | `JNINativeMethod[]` tables |
| JNI wrapper functions | `generated/jni/` | Thin C++ JNI bridge functions |
| Native C API headers | `generated/native/` | Internal C API used by bindings |
| Luau binding functions | `generated/luau/` | `lua_CFunction` implementations |
| Luau registration tables | `generated/luau/` | `luaL_Reg[]` tables |
| API Documentation | `generated/docs/` | Markdown reference |
| Unit test skeletons | `generated/docs/` | Test scaffolding |

---

## 3. File Naming Convention

Generated files use `.gen.` in their name:

| Language | Pattern | Example |
|----------|---------|---------|
| Kotlin | `<Class>.gen.kt` | `Document.gen.kt` |
| JNI header | `<Class>.gen.hpp` | `Document.gen.hpp` |
| JNI impl | `<Class>.gen.cpp` | `Document.gen.cpp` |
| Luau binding | `<Class>.gen.luau.cpp` | `Document.gen.luau.cpp` |
| Docs | `<Class>.gen.md` | `Document.gen.md` |

Every generated file starts with:
```kotlin
// ============================================================
// AUTO-GENERATED FILE — DO NOT EDIT MANUALLY
// Generated by: Luandro Binding Generator
// Source: spec/lexsoup/Document.yaml
// Regenerate: run `./gradlew generateBindings`
// ============================================================
```

---

## 4. Input (ASL Specification)

The generator consumes `.yaml` files from `spec/`:

```
spec/
  lexsoup/
    Document.yaml       ← HTML document
    Element.yaml        ← DOM element
    Elements.yaml       ← element collection
    Node.yaml           ← DOM node
  regex/
    Pattern.yaml        ← compiled regex pattern
    Matcher.yaml        ← pattern matcher
    MatchResult.yaml    ← single match result
  js/
    Runtime.yaml        ← QuickJS runtime
    Context.yaml        ← JS execution context
    Module.yaml         ← ES module
  luau/
    VM.yaml             ← Luau VM
    Script.yaml         ← compiled script
```

## 5. Build Integration

```
spec/ changes detected
        │
        ▼
generateBindings task (Gradle)
        │
        ▼
generated/ updated
        │
        ▼
compileDebugKotlin / CMake build
```

Gradle task dependency:
```kotlin
tasks.named("compileDebugKotlin") {
    dependsOn("generateBindings")
}
tasks.named("configureCMakeDebug") {
    dependsOn("generateBindings")
}
```

## 6. Custom Code Extension Points

For non-standard behavior, developers extend generated classes in manual files:

```
Manual file:    kotlin/io/github/luandro/lexsoup/DocumentExtensions.kt
Generated file: generated/kotlin/lexsoup/Document.gen.kt
```

```kotlin
// Document.gen.kt (GENERATED — do not edit)
open class Document internal constructor(val handle: Long) : Closeable {
    fun title(): String = nativeTitle(handle)
    // ...
}

// DocumentExtensions.kt (MANUAL — your custom code)
fun Document.titleOrEmpty(): String = title().ifEmpty { "" }
```

---

## 7. Regeneration Policy

When an ASL spec changes:
1. Run `./gradlew generateBindings`
2. Compile and verify
3. Run tests
4. **Never manually edit** the regenerated files

---

## 8. Success Criteria

Adding a new public API requires ONLY:
1. Add/update `.yaml` file in `spec/`
2. Run the generator
3. Implement the native function in `native/`
4. Compile and test

**No manual JNI, Kotlin wrapper, or Luau binding is required.**
